# 性能验证报告

## 1. 测试环境

| 项 | 值 |
|---|---|
| 主机 | Windows 10，4 逻辑 CPU，8 GB RAM |
| 服务端 | Paper 1.18.2（JDK 17），`view-distance=4`、`simulation-distance=4`、`max-players=300` |
| 客户端 | 200 × mineflayer 机器人（离线模式，关闭物理），独立 Node 进程 |
| 插件 | BentoMenu 1.0.0 + BentoTestHarness（测试经济/命令）+ Vault 1.7.3 + PlaceholderAPI 2.11.6 |
| 菜单 | 默认 `shop`：5 行，14 个内容槽，18 个条目，4 个分类，5 秒自动刷新，18 条目均含 `{balance}` |
| 采样 | `/bentotest status` 每 5 秒：`Bukkit#getTPS` 与 `getAverageTickTime`；插件 `/bento stats` 记录渲染/点击耗时 |

> 说明：客户端机器人也在同一台 4 核主机上运行，会占用 CPU 与内存；因此下表中的服务端 TPS 是偏保守的。

## 2. 分阶段结果（最终 jar，修复 PAPI 缓存后）

| 阶段 | 在线 | TPS（1/5/15 分钟） | 平均 tick | 说明 |
|---|---|---|---|---|
| 空闲、菜单关闭 | 200 | 20.00/20.01/20.00 | 16.8–18.1 ms | 200 人在线基线 |
| 200 个菜单同时打开、无人点击 | 200 | 19.78/19.96/19.99 → 20.00/20.01/20.00 | 29.5–37.9 ms | 同一 tick 内由 RCON 打开全部菜单 |
| 全部关闭 | 200 | 20.00/20.01/20.00 | 14.2–15.0 ms | 回到基线 |
| 重新打开 + 持续点击 | 200 | 19.25–20.55/19.85–19.95/19.95–19.99 | 44.1–56.5 ms | 30 秒内 2,225 次点击（约 74 次/秒，随机点内容槽并触发购买） |

结论：

- **200 人同时打开菜单**：打开瞬间的 1 分钟 TPS 采样为 19.78（单次采样），随后稳定 20.00；没有出现“Can't keep up”持续掉刻。
- **200 人同时在线且有菜单打开**：TPS 保持 20.00。
- **持续点击压力**（远超正常交互频率，约 74 次/秒）：TPS 为 19.25–20.0（≥96%），tick 仍低于 50ms；这是 200 个客户端与 4 核主机共同作用的结果，而非单次点击阻塞（见下）。

## 3. 插件自身耗时

`/bento stats`（最终 jar，200 bot，总计 400 次打开、2,043 次点击、5,632 次渲染）：

| 指标 | 数值 |
|---|---|
| 平均点击处理 | **0.061 ms** |
| 最大点击处理 | **3.23 ms** |
| 平均渲染（全量槽位数组 + 差异更新） | **4.00 ms** |
| 最大渲染 | **64.94 ms**（首次/JIT 冷启动） |
| 物品更新总数 | 38,680（差异更新，未整包重发） |

点击路径中不含磁盘 I/O、网络 I/O 或 PAPI 同步解析；经济与占位符均为缓存/本地调用。

## 4. 点击到反馈延迟

### 4.1 本机直连

`probe.mjs`：记录从发送点击包到收到反馈声音包的时间。

| 轮次 | 菜单打开 RTT | 点击 → 声音 |
|---|---|---|
| 1 | 7.99 ms | 3.64 ms |
| 2 | — | 2.24 ms |
| 3 | — | 0.96 ms |
| 4 | — | 0.99 ms |
| 5 | — | 0.95 ms |

远低于 100ms 目标。

### 4.2 注入 200ms 网络延迟

`latency-proxy.mjs` 对每个方向延迟 100ms（RTT ≈ 200ms），客户端连代理端口：

| 指标 | 结果 |
|---|---|
| 菜单打开 RTT | 220.54 ms |
| 点击 → 声音 | 217.46、218.08、218.22、220.31、220.33 ms |

差值约 17–20ms，包含代理转发与 TCP 排队；服务端在收到点击后立即处理并回包，没有额外等待。5/5 次点击均收到反馈，菜单保持响应。

## 5. 大量数据/刷新

- 每个会话的刷新请求在 1 tick 内合并；渲染逐槽 `Objects.equals` 差异，只发送变化槽。
- 5,632 次渲染中 38,680 次物品更新，平均 6.9 槽/渲染，说明未发生整包重发。
- 过滤/搜索在独立线程池执行，结果按代次丢弃过期任务；200 个会话同时刷新时，异步线程不占用主线程。
- 资源包禁用时边框为染色玻璃，渲染路径不涉及资源包解码。

## 6. 已知边界

- 首次打开菜单会构建完整 45 槽物品数组；在 200 个会话同一 tick 打开时，平均 tick 会升至约 38ms，但 TPS 仍为 20（最终采样）。
- 极端连续点击（74 次/秒）在本机 4 核环境中使 TPS 落到 19.25–20.0；正常玩家交互频率远低于此。
- `max-render-ms` 64.94ms 为冷启动/JIT 峰值；稳定期平均 4ms。
- Folia 与 26.x 未做 200 bot 压测（26.3 协议不被 mineflayer 支持；Folia 仅验证功能与启动）。

## 7. 复现命令

```bash
# 200 bot 分阶段基准
node tools/loadtest/bench.mjs 127.0.0.1 25565 25575 200 1.18.2 BF

# 直连延迟探针

# 200ms RTT 代理 + 探针
node tools/loadtest/latency-proxy.mjs 25566 127.0.0.1 25565 100
node tools/loadtest/probe.mjs 127.0.0.1 25566 1.18.2 LatencyProbe 5
```
